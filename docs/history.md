# History

What happened in OnCue's development, in date order: what was built, what was decided, what was verified and how, and what stayed open. Each section starts with the date or date range it covers (UTC). Decisions are explained in [decisions.md](decisions.md); the current design is in [architecture/](architecture/README.md); open work is in [roadmap.md](roadmap.md) and [backlog.md](backlog.md).

Plan-step ids (`PR-01` to `PR-16`) come from the original implementation plan. They are not GitHub pull request numbers; D1 migrations still cite them. Pull request numbers here and throughout (`GitHub #N`) are from the project's private development repository, so they are not links.

This is a working log, not documentation: where it disagrees with the architecture records, the records describe the code. "The owner" is the project's maintainer, and "hosted" means the maintainer's own deployment. [Terms](architecture/README.md#terms) defines the rest of the vocabulary.

## 2026-09-01 · Architecture records and the pre-implementation review

The 25 architecture records (00 to 24) were written before any code. A two-round review on 2026-09-01 audited them against primary provider documentation and found no defect that made the system unbuildable, but ten high-severity problems that would have caused a security incident or a stalled build. All were corrected in the records the same day (see [decisions.md](decisions.md)). Among them:

- Cloudflare Workers cannot call Modal's SDK (it needs gRPC and a Node, Deno, or Bun runtime), so a Modal-hosted Python sandbox controller was added between the control plane and Modal.
- The GitHub App install flow trusted the `installation_id` on the setup URL, which GitHub documents as spoofable. Linking now requires a user access token and `GET /user/installations`, and the user and refresh tokens are kept, sealed, so access can be revalidated at session start.
- Previews had to move to a separate registrable origin, reached through a single-use code and a host-only partitioned cookie.
- The bridge is not a trust boundary from the agent unless they run as different Unix users. The records now require privilege separation, a defined path for the bootstrap credential, per-operation GitHub tokens that are actively revoked, bridge-performed pushes, and a push-webhook audit.
- The review first concluded Modal could not express the intended network policy, then retracted that: `outbound_domain_allowlist=["*"]` with no CIDR allowlist was made the candidate, provisional until a live test.
- Open registration with operator-funded compute had no cap. The owner replaced it with an operator-managed allowlist and per-workspace and platform-wide concurrent-sandbox caps.

The owner also decided the four open questions: the allowlist (H6), `policy.propose` as the chat-to-policy mechanism (M4), the preview origin design (H3, H7), and operator identity (L2). Medium findings fixed state-diagram disagreements, missing event families, D1-versus-object creation ordering, WebSocket authentication, subagent disablement, and the 24-hour Modal ceiling.

Verdict: ready to begin implementation planning, with two provider questions left as gates before the sandbox image was finalized or anyone but the owner was admitted: the Modal network policy (feasibility test A) and the bridge-isolation mechanism (test B, a Modal sidecar, or test C, Unix users in one container). A written test plan for both was approved the same day. The implementation plan, sixteen steps PR-01 to PR-16, followed on 2026-09-02; it chose to build the session event log first, before sign-in or the sandbox.

## 2026-09-09 · Sandbox controller, Modal driver, bridge skeleton, and feasibility tests (PR-08 · GitHub #17, merged)
Built: `services/sandbox-controller`, a stateless FastAPI app on Modal exposing the eight driver operations plus a read-only connection test, holding no Modal credential of its own (each request carries the workspace's pair); idempotent `create` by lookup, create, and lookup again, since Modal has no create-or-get; one sandbox image with Unix-user separation and the network policy `outbound_domain_allowlist=["*"]` with no CIDR list; the Modal driver in the Worker, selected only when the controller bindings and the workspace's Modal credential are both present; the bridge skeleton (connect outbound, negotiate the protocol version, heartbeat, answer shutdown) with a loopback relay; the `modal_connection` row and migration `0005_modal_connections.sql`; the setup step and settings screen for Modal; and the timeline's action rows. The controller was deployed by hand to the operator's Modal workspace.

Decided: test B closed on provider availability, so the bridge uses Unix-user separation; the Modal SDK is pinned exactly at 1.5.5. See [decisions.md](decisions.md).

Verified on real Modal on 2026-09-09, with the operator's authorization:

- Test A passed in two real sandboxes, the candidate policy against Modal's default egress as a comparison. DNS works through Modal's resolver; HTTPS on 443 works; an authenticated public API is reachable and answers 401. Plain HTTP on 80, raw TCP, UDP (including DNS to public resolvers), all three RFC 1918 ranges, link-local, and `169.254.169.254` are blocked. Private and metadata destinations are blocked under both policies; HTTP, raw TCP, and UDP only under the candidate. Observed and recorded: some blocks hang to the socket timeout rather than failing fast; IPv6 egress appears unavailable; enforcement looks SNI-based (one probe); where a denial is logged was not established.
- Test B was not run. Modal restricts Sandbox Sidecars to allowlisted workspaces, which OnCue cannot obtain for each user's workspace; the credential-injecting proxy mode also cannot be combined with a domain allowlist. Isolation was not measured, so no isolation conclusion follows.
- Test C passed on the real image after three image findings were fixed: the entrypoint script could not be written by `run_commands`; the bridge home was recreated root-owned and world-listable by a later layer; and twelve setuid or setgid files (including `su` and Chromium's sandbox helper) survived being stripped or deleted in the image, because Modal's image capture keeps additions but not deletions or mode changes to files from the apt layer. They are now removed at container start. Every escalation check then failed to escalate. Also observed: a process started through `Sandbox.exec` inherits the container's base environment, Modal Secret included, whatever user it runs as, so the controller's `execute` unsets the bootstrap variable and agent commands are only ever started by the bridge with a clean environment.
- Lanes 6 to 10 passed: a retried `create` returned the same sandbox, a stale-generation bridge was closed with 4000, a zero workspace cap refused the start before Modal, an unauthenticated call from a sandbox reached the Worker and got 401 (Cloudflare's edge refuses Python's default User-Agent with error 1010 before the Worker), and a stop converged. Cold create on the cached image took 8.4 to 16.2 s.

What the feasibility results allowed from then on: records may describe the network policy and the Unix-user bridge boundary as tested, with the observations above. They may not claim anything about sidecar isolation, may not treat an SDK upgrade (1.6.0 changes the sandbox backend) as a version bump, and must re-run test C on any change to the image, the entrypoint, or the users inside it. The boundary is defence in depth within one container: anything that escalates to root defeats it, and nothing observed shows a path to that.

Open at merge: `runtime.ready` could not be observed until `/ws/bridge` was deployed; a superseded generation's sandbox was never terminated (PR-10 fixed it); the controller has no notion of a current generation; a controller 401 is reported as OnCue's credential even when the user's Modal token was revoked.

## 2026-09-15 · Durable Object read-limit incident (GitHub #25 and #26)

Over about three minutes on 2026-09-15, one hosted session's Durable Object received about 300 WebSocket messages a second from its bridge and refused every one. The hour read 24.5 million rows against the plan's limit of 5 million a day, and Cloudflare blocked every Durable Object request on the account. It cost nothing (a free-plan limit blocks rather than bills) and made the hosted app unusable.

Cause, two defects that multiplied:

- Cost: every inbound bridge frame read every event id of the generation before admission decided anything, and no index served that query, so each refused frame scanned the log (about 462 rows per invocation on a session of about 453 events).
- Volume: on a frame ahead of the expected sequence the object asked for a replay with no bound. Once the missing frame had fallen out of the bridge's 512-frame ring, the bridge re-sent what it held, starting at the same gap, and the two traded that exchange as fast as the socket allowed.

What started the loop is unknown: the hosted Worker kept no logs, the refused frames were never stored, and the sandbox's logs were gone a day later.

Fix: GitHub #25 (merged 2026-09-15) made the duplicate check one lookup on the unique `event_id` index, added indexes on `event` by type and generation and by generation (built on the object's next wake), and made the last-activity read stop at the first qualifying event: 461 rows per refused frame became 2. GitHub #26 (merged 2026-09-16) bounded the object's replay asks at `MAX_REPLAY_ASKS` (3) per socket, after which it logs `replay_unavailable` and closes the socket with 4001, and made the bridge send nothing when its ring cannot reach back. Both were deployed through CI, the second as release `4be0de2`. The account stayed blocked through 2026-09-16; a bridge upgrade reached the object and got 101 on 2026-09-17.

Lesson: every read on a hot path (every bridge frame, every rearm, every client message) needs an index that serves its `WHERE` and `ORDER BY`, and every loop between the object and the bridge is bounded on the object's side, because the sandbox is untrusted. `session-read-cost.test.ts` fails when a frame's average read passes 40 rows on a long log (45 since 2026-09-27); Miniflare has no quotas, so it is the only local instrument. The rule now lives in [01-control-plane.md](architecture/01-control-plane.md). PR-12 enabled Workers Logs on the hosted Worker.

Still open: no one has read a hosted session's rows-read count from Cloudflare's analytics since the fix; record 04's designed recovery for a gap larger than the ring is not built; on Workers Free any daily limit blocks the whole account, and a few busy streaming sessions could reach the 100,000-request limit with no bug.
